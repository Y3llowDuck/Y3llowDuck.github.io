PHP2Shell: What to Do Before the Patch Lands

Pre-auth RCE CVSS 9.2 ~9 min read

Two things in this post, and I want the line between them clear up front. The first part is what the PHP advisories actually say. The second part is general hardening I'd do on anything I can't patch right away. The advisories only cover a narrow slice. Don't read my hardening advice as if it came from the PHP Foundation, because it didn't.

The short version: patch now. Everything else buys you time, nothing else fixes the bug.

01 — what php2shell is

Two bugs, one nickname

PHP2Shell is the name stuck on two flaws: CVE-2026-109618 and CVE-2026-109619. Both are unauthenticated remote code execution in PHP itself, not in a framework or a plugin. Both score 9.2 on CVSS 4.0. They were published on October 21, 2026, and credited to a researcher going by Calif. A working proof of concept leaked before the patches shipped, which is the part that should make you nervous.

  • CVE-2026-109618 abuses how PHP aborts a request when it runs out of memory.
  • CVE-2026-109619 abuses request state that survives after its memory is freed.

Confirmed attack paths run through Apache mod_php and PHP-FPM. That covers a huge amount of the PHP serving the web. Early reports on exploitation didn't agree with each other. Some described opportunistic waves dropping web shells and cryptominers, others mentioned ransomware and APT activity. When the reporting is that mixed this early, treat it as "assume someone is trying" rather than waiting for a clean consensus.

02 — the only complete fix

Patch. That's it.

The fixed releases are 8.5.12, 8.4.27, 8.3.36 and 8.2.35. PHP 8.1 and older are end of life, so there is no upstream fix for them. If you're still on 8.1 or below, patching isn't a version bump, it's a migration, and you should have started already.

don't trust the version number
Distro packages may backport the fix without changing the version string. So a box reading "8.2.20" could already be patched, or could be wide open. Verify against the vendor's changelog, not the number php -v prints.
03 — temporary mitigations

From the PHP project, and only partial

The PHP project published mitigations for installs that can't patch yet. Read the word "temporary" the way they meant it. These reduce the odds, they don't close the hole, and every one of them needs all workers restarted to take effect.

php.ini / fpm pool — partial mitigation
; restart all workers after changing these memory_limit = -1 post_max_size = 8M session.upload_progress.enabled = 0 fatal_error_backtraces = 0 pm.max_requests = 1

A few of these aren't obvious, so here's what each one is doing.

memory_limit=-1 looks backwards. You're removing a limit to get safer? Yes, because the first bug relies on the controllable memory limit failure, and taking that away removes the path it leans on. It is not a clean win though. An underlying allocation failure can still reach the vulnerable code. So enforce it at the admin level so applications can't override it, and check that no pool or directory setting quietly puts a finite limit back. Then replace the limit you just removed with a container or cgroup boundary. Do not reach for RLIMIT_AS or RLIMIT_DATA to do it, because those can trigger the exact allocation failure the exploit wants.

post_max_size=8M fits apps that don't need large uploads. If yours does, this one will hurt.

session.upload_progress.enabled=0 blocks only the confirmed session paths for the second bug. Narrow, but cheap.

fatal_error_backtraces=0 applies to PHP 8.5 only. On older branches it does nothing for you.

pm.max_requests=1 recycles each FPM worker after a single request, which kills the stale-state reuse. It also costs you real performance, so this is the one you'll want to back out first once you've patched.

Set these in php.ini or the FPM pool, not in .user.ini or ini_set(), so an application can't walk them back at runtime. If an app doesn't accept multipart form data at all, just block it at the frontend and be done. The PHP Foundation also suggests a WAF in front of exposed servers, while saying plainly that none of this makes an install safe. Believe them.

04 — harden what you can't patch

My recommendations, not the advisory's

Everything from here down is me, not the PHP Foundation. It's also the part I actually care about: what I'd do on AWS for anything exposed that I can't patch on the spot. None of it fixes the bug. It cuts how reachable the bug is, then boxes in whatever runs if someone gets through anyway.

Read the diagram top to bottom. That's the order an attacker's packet travels, and every layer is built to assume the one above it failed.

Layer 1: cut reachability at the edge

Put CloudFront or an ALB in front and lock the origin security group to the CloudFront managed prefix list, so nothing reaches the origin directly. Add authentication at the edge, ALB OIDC or Cognito, or move the app behind a VPN or ZTNA. If an unauthenticated request never reaches PHP, a pre-auth RCE has nothing to talk to. That one step does more than every php.ini tweak combined.

Then use AWS WAF for what it's actually good at, which is shrinking the attack surface, not stopping the exploit. Cap request body size. Both bugs are memory going wrong under load, and the first one leans on large request handling, so a hard ceiling on POST size at the edge backs up post_max_size and refuses oversized bodies before they ever reach a worker. Block multipart uploads on routes that don't accept them. Rate limit. If an app takes no multipart data at all, drop it at the edge and move on.

Cap response size too, which people forget. A pre-auth RCE that lands gets used to read things and ship them back out, and bulk is how stolen data and directory dumps leave. A login endpoint returning a 40MB body is both a limit worth enforcing and an alert worth firing. Keep the normal responses small and the abnormal one gets loud.

A vendor virtual patch, like the Cloudflare protections reported for this flaw, is a reasonable layer on top of all this, not a replacement for any of it.

Layer 2: tighten the network

Reference security groups by group id, not CIDR, so the web tier accepts 443 from the load balancer's SG and nothing else. Give it only the specific app and database ports it needs outbound, and never a route to management or directory services. The blast radius of a shell on that box should be that box.

Default deny egress on the web tier. AWS Network Firewall with a domain allowlist, plus Route 53 Resolver DNS Firewall, means a dropped web shell can't resolve its command-and-control, can't phone home, and can't pull a second stage. A lot of commodity exploitation just dies here, because the payload assumes it can reach the internet and it can't.

egress filtering alone isn't enough
An attacker already inside the web tier can still reach your secrets and whatever paths you did allow. Blocking outbound is one wall, not the building. That's the whole reason for least-privilege roles and tight segmentation sitting next to it.

Layer 3: contain the host

Assume something runs anyway and make it worthless. Enforce IMDSv2 with hop limit 1 and strip the instance role to the minimum, so a foothold doesn't turn into stolen AWS credentials. Run PHP as a non-root user, mount the webroot read-only, and set noexec on anything writable, so a web shell can't drop and run a binary. Small changes, ugly payoff for the attacker.

Layer 4: see it, then rank it

You can't harden what you can't see, so inventory first. I'd use Wiz to find PHP versions across the estate and rank assets by internet exposure and attack paths, so the internet-facing 8.1 box gets your attention before the internal one. For detection, Falcon to alert on php-fpm, httpd or apache2 spawning shells, curl, wget or interpreters, and to hunt for web shells with RTR. On AWS, GuardDuty Runtime Monitoring and Malware Protection, VPC Flow Logs, Inspector, and SSM to push config at scale.

One detection note worth keeping: vendors are treating PHP crashes and memory exhaustion errors as likely signs of exploitation. Both bugs are about memory going wrong, so a sudden run of those in your logs is a lead, not noise.

05 — assume exposure

If it was exposed, go hunt

The proof of concept leaked before the patches landed. That ordering matters. It means there was a window where exploit code existed and fixes didn't, so mitigation after the fact doesn't tell you that nothing happened during it. On any asset that was exposed, hunt for compromise, even one you've since mitigated or patched. Clean today does not mean clean last Tuesday.

before you rely on anything here
I pulled the mitigation details from secondary sources that quote the PHP project, and that guidance can change. Check the PHP project's own advisory pages before you act on this, especially the php.ini values. On a pre-auth RCE you want the primary source, not a blog, including this one.
