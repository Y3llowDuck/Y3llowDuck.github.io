PHP2Shell: Before the Patch

Pre-auth RCE CVSS 9.2 ~9 min read

Any security vulnerability that ends in an actual RCE is a major headache. And the actual fix is a patch. There's no workaround. But the problem with patches is the implied downtime and the testing they require. We do not want to patch a critical asset without testing. At least, that's the recommended approach.

So I want to give some perspective on the temporary mitigations we must take when something like PHP2Shell appears in the wild. And I want to put emphasis on the word temporary, because these kinds of issues can only be fixed with an actual patch. Otherwise, we must accept the risk and the potential consequences.

Regardless, I want to explain some of the mitigations that can be taken, using PHP2Shell as an example. These same concepts are not new and can be implemented at any time on pretty much any app design in AWS. In practice they can be the difference between getting hit by a major vulnerability with no data leak, or getting hit and ending with a crashed server, downtime, and company reputation affected.

The short version: patch now. Everything else buys you time, nothing else fixes the bug.

01 — what php2shell is

Two bugs, one nickname

PHP2Shell is the name stuck on two flaws: CVE-2026-109618 and CVE-2026-109619. Both are unauthenticated remote code execution in PHP itself, not in a framework or a plugin. Both score 9.2 on CVSS 4.0. They were published on October 21, 2026, and credited to a researcher going by Calif. A working proof of concept leaked before the patches shipped, which is the part that should make you nervous.

  • CVE-2026-109618 abuses how PHP aborts a request when it runs out of memory.
  • CVE-2026-109619 abuses request state that survives after its memory is freed.

Confirmed attack paths run through Apache mod_php and PHP-FPM. That covers a huge amount of the PHP serving the web. Early reports on exploitation didn't agree with each other. Some described opportunistic waves dropping web shells and cryptominers, others mentioned ransomware and APT activity. When the reporting is that mixed this early, treat it as "assume someone is trying" rather than waiting for a clean consensus.

02 — the only complete fix

Apply the Patch

The fixed releases are 8.5.12, 8.4.27, 8.3.36 and 8.2.35. PHP 8.1 and older are end of life, so there is no upstream fix for them. If you're still on 8.1 or below, patching is a migration, and you should have started already.

don't trust the version number
Distro packages may backport the fix without changing the version string. So a box reading "8.2.20" could already be patched, or could be wide open. Verify against the vendor's changelog, not the number php -v prints.
03 — temporary mitigations

From the PHP project

The PHP project published mitigations for those installations that cannot be patched yet. But read the word "temporary" as what it is, a temporary workaround. These workarounds reduce the chances of being compromised, they don't eliminate the security hole, and every one of them needs all workers restarted to take effect.

what is a PHP-FPM worker?
PHP-FPM (FastCGI Process Manager) manages a pool of PHP processes that handle incoming web requests. Think of each process as a worker sitting on standby: when a request arrives, a worker picks it up, runs the PHP code, and sends the response back. The worker then goes back to standby, and here's the problem. It may still hold data in memory from the previous request. CVE-2026-109619 exploits exactly this: it abuses that leftover memory to gain control of the process. The mitigations below all attack different parts of this same problem.
php.ini / fpm pool — partial mitigation
; restart all workers after changing these memory_limit = -1 post_max_size = 8M session.upload_progress.enabled = 0 fatal_error_backtraces = 0 pm.max_requests = 1

A few of these aren't obvious, so here's what each one is doing.

memory_limit=-1 looks backwards. You're removing a limit to get safer? Yes, because the first bug relies on the controllable memory limit failure, and taking that away removes the path it leans on. It is not a clean win though. An underlying allocation failure can still reach the vulnerable code. So enforce it at the admin level so applications can't override it, and check that no pool or directory setting quietly puts a finite limit back. Then replace the limit you just removed with a container or cgroup boundary. Do not reach for RLIMIT_AS or RLIMIT_DATA to do it, because those can trigger the exact allocation failure the exploit wants.

post_max_size=8M fits apps that don't need large uploads. If yours does, this one will hurt.

session.upload_progress.enabled=0 blocks only the confirmed session paths for the second bug. Narrow, but cheap.

fatal_error_backtraces=0 applies to PHP 8.5 only. On older branches it does nothing for you.

pm.max_requests=1 tells PHP-FPM to retire each worker process after handling exactly one request, then spawn a fresh one for the next. A fresh process has no leftover memory from anything previous, which removes the stale-state that CVE-2026-109619 depends on. The tradeoff is real: spawning a new process per request is slow, so this one hurts performance and should be the first setting you remove once you've patched.

Set these in php.ini or the FPM pool, not in .user.ini or ini_set(), so an application can't walk them back at runtime. If an app doesn't accept multipart form data at all, just block it at the frontend and be done. The PHP Foundation also suggests a WAF in front of exposed servers, while saying plainly that none of this makes an install safe. Believe them.

04 — harden what you can't patch

AWS Infrastructure

Everything from here down is me, not the PHP Foundation. It's about what someone should do on an AWS tenant for anything exposed that cannot be patched right away. None of it fixes the bug though, so keep that in mind. It only reduces the blast radius or cuts our losses, in plain Texas hold'em terms.

Read the diagram top to bottom. That's the order an attacker's packet travels, and every layer is built to assume the one above it failed.

Layer 1: cut reachability at the edge

Put CloudFront or an ALB in front and lock the origin security group to the CloudFront managed prefix list, so nothing reaches the origin directly. Add authentication at the edge, ALB OIDC or Cognito, or move the app behind a VPN or ZTNA. If an unauthenticated request never reaches PHP, a pre-auth RCE has nothing to talk to. That step does more than every php.ini tweak combined.

Then use AWS WAF for what it's good at, which is shrinking the attack surface.

Cap request body size. CVE-2026-109618 triggers when PHP runs out of memory processing a request. The larger the request body, the more memory PHP has to allocate for it. An oversized POST body, especially a multipart file upload, is exactly what pushes PHP toward that memory limit and into the abort path the exploit abuses. A hard ceiling on POST body size at the WAF means PHP never receives that request: the allocation never happens, the memory pressure never builds, and the exploit path closes before it starts. This also reinforces whatever you set in post_max_size, giving you two enforcement points instead of one. Block multipart uploads entirely on routes that don't use them. If an endpoint has no reason to accept a file, tell the WAF to drop multipart requests to it outright. Rate limit everything else.

Cap response size too, which people forget. This one is easy to overlook because it feels like a performance setting, not a security one. But if an RCE does land, the attacker's goal is to read files and get data out. That data has to leave as HTTP responses. A normal page load returns a few kilobytes. A directory listing, a file read, or a database dump returns megabytes. A WAF rule that rejects responses over a reasonable threshold catches that bulk exfiltration even when the inbound request looked perfectly fine. A login endpoint returning 40MB is not normal: it is worth capping and worth alerting on.

A vendor virtual patch, like the Cloudflare protections reported for this flaw, is a reasonable layer on top of all this, not a replacement for any of it.

Layer 2: securing the network

Reference security groups by group id, not CIDR, so the web tier accepts 443 from the load balancer's SG and nothing else. Give it only the specific app and database ports it needs outbound, and never a route to management or directory services. The blast radius of a shell on that box should be that box.

Default deny egress on the web tier. AWS Network Firewall with a domain allowlist, plus Route 53 Resolver DNS Firewall, means a dropped web shell can't resolve its command-and-control, can't phone home, and can't pull a second stage. A lot of commodity exploitation just dies here, because the payload assumes it can reach the internet and it can't.

egress filtering alone isn't enough
An attacker already inside the web tier can still reach your secrets and whatever paths you did allow. Egress filtering alone does not protect you. That's the whole reason for least-privilege roles and tight segmentation sitting next to it.

Layer 3: hardening the host

what is IMDSv2?
IMDS stands for Instance Metadata Service. It is an endpoint that every EC2 instance can reach at 169.254.169.254 to ask AWS for information about itself, including its IAM credentials. IMDSv2 is the newer, more secure version: it requires a session token before returning anything, so a simple HTTP request from an attacker's shell is not enough to get the credentials. Setting hop limit 1 means the request can only come from the instance itself, not from a container or process one network hop away.

Even if the exploit lands, you can limit how much damage it does. IMDSv2 with hop limit 1 blocks a shell from querying the EC2 metadata service to steal AWS credentials. A minimal instance role means even if it does get credentials, there is nothing useful attached to them. Run PHP as a non-root user, mount the webroot read-only, and set noexec on anything writable, so a web shell can't drop and execute a binary. The goal is to make the foothold as useless as possible.

Layer 4: inventory

You can't harden what you can't see, so inventory first. I'd use Wiz to find PHP versions across the estate and rank assets by internet exposure and attack paths, so the internet-facing 8.1 box gets your attention before the internal one. But any bash script can do basically the same.

bash — find exposed PHP servers in a subnet
# find live web hosts in the subnet nmap -p 80,443 --open -oG - 10.0.1.0/24 \ | awk '/open/{print $2}' > live_web.txt # check each host for vulnerable PHP nuclei -l live_web.txt -tags php -severity critical,high
how to install nuclei
Nuclei is a fast, template-based vulnerability scanner by ProjectDiscovery. To install it, you need Go on your system. Then run:

go install -v github.com/projectdiscovery/nuclei/v3/cmd/nuclei@latest

On Kali Linux it is also available via apt:

sudo apt install -y nuclei

Either way, pull the latest templates before you scan: nuclei -update-templates
05 — logs & detection

Always check your logs

Some of the biggest breaches in history were detected weeks or months after the initial compromise. Two that come to mind: the Target POS breach in 2013, where FireEye alerts fired and went unacknowledged for weeks before external researchers flagged the compromise, and the VTech breach in 2015, where millions of children's records were stolen before the company knew anything had happened. Checking your logs is never a bad idea.

Vendors are treating PHP crashes and memory exhaustion errors as likely signs of exploitation. Both bugs are about memory going wrong, so seeing a run of those in your logs is not good news. On any exposed asset, check the Apache or nginx access and error logs. Inspect the firewall logs. Look for abnormal outbound traffic from any PHP host, especially to unfamiliar destinations. That is a strong indicator that an RCE was executed.

Some administrators hash key directories for file integrity monitoring, particularly read-only ones. If a hash changes and you can correlate it with a web server or firewall log anomaly, you have a much clearer picture of a potential breach.

If you use Falcon it can also assist with alerts on php-fpm, httpd or apache2 spawning shells, curl, wget or interpreters, and with hunting for web shells via RTR. On AWS, GuardDuty, VPC Flow Logs, and Inspector are useful here as well.

before you rely on anything here
Check the PHP project's own advisory pages before you act on this, especially the php.ini values. This is a serious vulnerability. The vendor's technical advice should always be your primary source.
